# LeetSync Spring Boot Backend

Backend service for a browser extension that syncs accepted LeetCode, Codeforces and GeeksForGeeks submissions to GitHub.

## Architecture

```text
Browser Extension
      |
      | Authorization: Bearer <GitHub OAuth token>
      v
Spring Boot REST API
      |
      +--> AuthService --------> GitHub /user
      |
      +--> GitHubSyncService
              |
              +--> CodeFileService
              +--> SubmissionFormatter
              +--> GitHubClient ------> GitHub REST API
```

The backend deliberately does **not** persist GitHub OAuth tokens. The extension owns token storage using `chrome.storage.local`; the backend receives the token only for the current request and uses it against GitHub.

## Requirements

- IntelliJ IDEA Ultimate
- Java 21+ (Java 24 should also work with this project setup)
- Gradle wrapper or Gradle 8+
- A GitHub repository where the OAuth token has permission to write contents

## Run in IntelliJ

1. Open the `leetsync-backend` folder.
2. Let IntelliJ import the Gradle project.
3. Set the project SDK to Java 21 or newer.
4. Run `LeetSyncApplication`.
5. The server starts on `http://localhost:8080`.

You can also run:

```bash
./gradlew bootRun
```

On Windows:

```powershell
gradlew.bat bootRun
```

## API

### Validate GitHub token

```http
POST /api/auth/github/validate
Authorization: Bearer <github-token>
```

A `401` response means the extension should clear its local token and re-authenticate through `chrome.identity`.

### Generic submission sync

```http
POST /api/sync/submission
Authorization: Bearer <github-token>
X-GitHub-Owner: your-github-username
Content-Type: application/json
```

Example:

```json
{
  "source": "LEETCODE",
  "problemId": "1",
  "problemTitle": "Two Sum",
  "language": "Java",
  "code": "class Solution { ... }",
  "repository": "dsa-solutions",
  "branch": "main",
  "runtime": "3 ms",
  "runtimePercentile": 98.2,
  "memory": "45 MB",
  "memoryPercentile": 80.1,
  "accepted": true
}
```

### Platform-specific endpoints

- `POST /api/sync/leetcode`
- `POST /api/sync/codeforces`
- `POST /api/sync/gfg`

All use the same JSON schema and require the corresponding `source` value.

## File layout generated in GitHub

```text
LeetCode/
  1-Two-Sum/
    solution.java
Codeforces/
  123A-Some-Problem/
    solution.cpp
GeeksForGeeks/
  two-sum/
    solution.py
```

The exact path is generated by `CodeFileService`.

## Duplicate/version handling

Before writing a file, the backend calls GitHub's contents API.

- File absent -> creates it.
- File exists and decoded contents are identical -> skips the commit.
- File exists with different contents -> updates the file using the existing SHA.

The browser extension can decide whether a submission is actually a performance improvement. The backend also prevents identical code from generating duplicate commits.

## Performance metrics

`SubmissionFormatter` prepends runtime and memory information as source-code comments. It supports values such as:

```text
// Runtime: 3 ms | Beats 98.2%
// Memory: 45 MB | Beats 80.1%
```

Because the formatter currently uses `//`, this works naturally for Java, C++, JavaScript, Python, etc. If you want language-specific comment syntax later, move that logic into a language strategy.

## Security notes

- Never log the OAuth token.
- Never put the token in query parameters.
- Keep the token in `chrome.storage.local` on the extension side.
- Send it as `Authorization: Bearer ...` only over HTTPS in production.
- Do not commit GitHub client secrets or OAuth credentials to this repository.
- For production, restrict CORS to the exact extension ID instead of the wildcard pattern used for local development.

## Important extension/backend contract

The backend does not scrape LeetCode. The extension remains responsible for:

1. Detecting `Accepted`.
2. Extracting problem ID/title/language/code.
3. Extracting runtime/memory metrics.
4. Detecting the platform.
5. Obtaining the GitHub OAuth token with `chrome.identity`.
6. Sending the normalized submission payload to this backend.

That separation keeps DOM-specific code out of Spring Boot and makes Codeforces/GFG support much easier.
